The CLI: dotnet assurance

The CLI builds one offline report from the evidence your tests recorded: for a whole solution, for an earlier run, or for some business areas only.

Install

dotnet tool install Ahr.Assurance.Cli

Set up a project

dotnet assurance init

Run it in each test project's folder, or once in a solution's folder. It writes ahr-assurance.json and adds no package. It reads the project's test framework from its package references, including versions set in Directory.Packages.props and MSTest.Sdk, and prints the command that adds the matching adapter:

dotnet assurance init --framework xunit-v3

With --framework, init adds those packages with dotnet add package, at the CLI's own version, then writes the config file. Name one test framework, and playwright beside it if you like, as a list or with --framework repeated: --framework xunit-v3,playwright.

Option What it does
--framework <names> Adds the Assurance packages for these: xunit-v3, xunit-v2, nunit, mstest (MSTest 4), mstest-v3, tunit, and the add-on playwright. In a solution's folder, sets up only the projects on that framework.
--force Writes ahr-assurance.json in a folder with no project file
  • An adapter that's already referenced is left as it is, and so is an existing ahr-assurance.json.
  • A --framework that contradicts the project, or a project that already references another adapter, stops init before any change. So does playwright alone in a project with no adapter for it to work beside.
  • When dotnet add package fails, for example offline or behind a feed without the adapter, init says so and writes no config file.
  • In a solution's folder, init sets up each test project and lists the projects it skipped.

The config file has a comment on each setting:

{
  // Each test run gets its own folder in here, named by its run ID. Relative to this file.
  "runs": "artifacts/assurance",
  // Remove older run folders beyond the newest 20 when a run starts.
  // "keep": 20,
  // Inside each run folder.
  "attachments": "attachments",
  "report": {
    // The report's title and the version shown after it. Without a title, the project's or solution's name.
    // "title": "Checkout",
    // "version": "4.2",
    // Inside each run folder.
    "output": "report",
    // Also write the report when 'dotnet test' finishes. 'dotnet assurance report' builds it either way.
    // "afterRun": true,
    // Business context IDs to leave out of the report, such as checks only developers read.
    // "excludeContexts": [ "technical" ]
  }
}

dotnet test only records evidence; the report comes from dotnet assurance report. To also write it as each test project's run finishes, set "afterRun": true, or pass --assurance-report on to dotnet test. In a pipeline, see Running in CI.

Report a run

dotnet test
dotnet assurance report

It runs like dotnet test: on the project or solution in the current folder, or the one you name. It reports the newest run of each project that has an ahr-assurance.json, in one report. A report covers one run, or one run across a solution. A solution's report is named after the solution, or by the report.title and report.version of an ahr-assurance.json beside it; the solution report reads nothing else from that file. A project in a subfolder needs an ahr-assurance.json of its own to be in the solution report. --title replaces both the title and the version.

The report of this repository's own tests shows what one looks like.

Option What it does
--run <id> Reports that run instead of the newest
--project <name> With a solution, reports only that project. Can be repeated.
--exclude-project <name> With a solution, leaves that project out. Can be repeated.
--context <id> Shows only that business context. Can be repeated.
--exclude-context <id> Leaves that business context out. Can be repeated. report.excludeContexts in the config does the same for every report.
--title <text> Names the report
--output <folder> Writes the report there
--input <folder> Reports evidence from that folder instead of the runs folder. Can be repeated.
--attachments <folder> Reads attachments from there, when they were moved or uploaded apart from the evidence
--developer Adds failure details, expected and actual values and test names

dotnet assurance report --help lists every option.

With --developer, a failed step shows what was expected and what came instead:

Exit codes

Code Meaning
0 Every recorded verification passed
1 The command, the evidence or the report couldn't be read or written
2 The report was written, and some verifications failed, were cancelled or didn't finish
130 Cancelled

Codes 1 and 2 are kept apart so a pipeline can tell a broken step from a report that shows failures.

The exit code covers the whole run, also when --context or --exclude-context leaves areas out of the report.
